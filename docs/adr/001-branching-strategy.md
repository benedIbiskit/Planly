## Контекст

Команда разрабатывает **Planly** — приложение для управления подписками: хранение сведений о сервисах, стоимости и датах следующих платежей для планирования расходов. Проект выполняется в рамках курса «Управление конфигурацией бизнес-приложений». Backend использует Python и FastAPI.

Характеристики проекта:

- Размер команды: 2 участника, указанных в README.
- Длительность: один семестр, 16 недель по учебному плану курса.
- Частота релизов: по готовности результатов практик и к учебным демонстрациям; отдельного производственного календаря релизов пока нет.
- Опыт с Git: команда выполнила практику №1 с веткой и PR. Индивидуальные уровни в документации не зафиксированы; процесс должен оставаться простым для освоения.
- Стабильность `main`: высокая, поскольку результат проверяют преподаватель и другие команды.
- В `CONTRIBUTING.md` уже описаны GitHub Flow и обязательное одобрение PR другим участником; ADR фиксирует обоснование выбора.
- CI предстоит внедрить на следующих этапах. Сейчас основа проверки — запуск приложения и ревью.

Нужна стратегия для параллельной работы над API и документацией, которая ограничит конфликты, сохранит работоспособность `main` и выполнит требования DoD курса: PR, approval и осмысленные коммиты.

## Рассмотренные варианты

### Вариант A: GitFlow

**Суть:** постоянные ветки `main` и `develop`, отдельные ветки функций, релизов и срочных исправлений. Изменения переносятся между линиями разработки по установленным правилам.

**Плюсы:**

- Подготовка релиза отделена от разработки следующих функций.
- Есть явный порядок сопровождения выпущенных версий.

**Минусы:**

- Дополнительные ветки и слияния увеличивают нагрузку на двух участников.
- Исправления нужно согласованно переносить между постоянными ветками.
- В Planly пока нет потребности сопровождать несколько версий одновременно.

**Подходит ли нам:** нет на текущем этапе; сложность процесса превышает пользу для учебного проекта.

### Вариант B: GitHub Flow

**Суть:** одна постоянная ветка `main`. Каждая задача выполняется в короткоживущей ветке от актуального `main` и возвращается через PR после проверки и одобрения.

**Плюсы:**

- Единый понятный процесс для функций, исправлений и документации.
- Небольшое число веток удобно для команды из двух человек.
- PR сохраняет обсуждение, результаты проверки и одобрение.
- Соответствует текущему `CONTRIBUTING.md` и требованиям DoD курса.

**Минусы:**

- Ошибки необходимо обнаруживать до интеграции: отдельной интеграционной ветки нет.
- При занятости второго участника ревью может задержаться.
- Крупные и долгоживущие ветки усложняют проверку и слияние.

**Подходит ли нам:** да; небольшие задачи и обязательное ревью позволяют сохранить простой процесс.

### Вариант C: Trunk-Based Development

**Суть:** очень частая интеграция небольших изменений в основную ветку, напрямую либо через короткие ветки и быстрые PR. Незавершённые функции при необходимости скрываются флагами; стратегия не исключает ревью.

**Плюсы:**

- Изменения участников меньше расходятся во времени.
- Небольшие порции изменений ускоряют обратную связь.

**Минусы:**

- Без быстрых автоматических проверок сложнее обеспечивать стабильность при частой интеграции.
- Нужна готовность оперативно проверять изменения, что зависит от учебного расписания.
- Флаги незавершённых функций требуют сопровождения и последующего удаления.

**Подходит ли нам:** с оговорками, после появления CI и тестов. Сейчас GitHub Flow удобнее для отдельных учебных задач с обязательным ревью.

## Решение

Предлагаем закрепить **GitHub Flow**, описанный в `CONTRIBUTING.md`.

Схема ветвления; возврат в `main` выполняется после ревью и approval:

```text
main                    A--------------B--------------C
                         \            / \            /
feature/subscriptions     o----o------/   \          /
docs/adr-001-branching-strategy            o----o----/
```

Правила работы с ветками:

1. `main` — стабильная основная ветка. Все изменения в неё поступают через PR; прямые push не используются.
2. Перед задачей выполнить `git switch main`, `git pull --ff-only origin main` и создать рабочую ветку от обновлённого `main`.
3. Префиксы веток: `feature/` — функции, `bugfix/` — исправления, `docs/` — документация, `hotfix/` — срочные исправления. После префикса указывается краткая цель: например, `feature/subscriptions`. Срочность не отменяет ревью.
4. Одна ветка и один PR решают одну задачу. Крупные изменения делятся на законченные части; ориентир — несколько дней на ветку, если задание курса не требует другого срока.
5. Для слияния нужен минимум один `Approve` другого участника. Автор отвечает на замечания; обсуждения закрываются до merge. После исправлений ревьюер проверяет актуальные изменения.
6. В PR описываются цель, изменения и проверка. Для кода проверяются запуск по README и `GET /health`; для документации — содержание, ссылки и согласованность с проектом. Результаты фиксируются в PR.
7. Коммиты следуют Conventional Commits: `feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`. Коммит содержит осмысленное изменение; секреты, `.env` и виртуальные окружения не включаются.
8. Перед интеграцией выполнить `git fetch origin`, при необходимости — `git merge origin/main` в рабочей ветке. После разрешения конфликтов повторить проверки. История общей опубликованной ветки не переписывается.
9. Предлагаемый способ слияния — Squash and merge с осмысленным итоговым сообщением. После слияния ненужная рабочая ветка удаляется.
10. **Защита `main`:** правила PR и approval заданы в `CONTRIBUTING.md`; фактические серверные настройки на дату ADR не подтверждены. Предлагаем владельцу проверить или настроить активный ruleset `protect-main`: PR с одним approval, сброс approval новыми коммитами, закрытие обсуждений до merge, запрет force-push и удаления `main`. Фактическое состояние фиксируется до принятия ADR. До практики №5 обязательные status checks не включаются; после внедрения CI их подключение оформляется отдельно.
11. Для этого задания публикуется только ветка `docs/adr-001-branching-strategy` с ADR в статусе «Предложено». PR открывается на практике №2 для межкомандного ревью. Согласование внутри команды и требование approval сохраняются.

## Обоснование решения

1. **Размер команды:** двум участникам достаточно одной основной ветки и веток задач. Постоянная `develop` добавила бы отдельный цикл синхронизации.
2. **Частота релизов:** результаты практик включаются по готовности после проверки; отдельный процесс релизных веток пока не нужен.
3. **Опыт команды:** стратегия продолжает процесс практики №1. Освоение не требует дополнительной модели релизов и переноса исправлений между постоянными ветками.
4. **Требования DoD:** PR, approval другого участника и содержательные коммиты входят в процесс. После внедрения CI можно добавить обязательные автоматические проверки.

## Последствия

### Положительные (+)

- Единый порядок изменения кода и документации.
- Проверка результата другим участником до попадания в `main`.
- История PR сохраняет причины изменений и обсуждение.
- Небольшие ветки уменьшают объём одновременно интегрируемых изменений.

### Отрицательные (-)

- Стабильность зависит от качества проверки до слияния.
- Недоступность второго участника задерживает PR.
- До появления CI ручные проверки занимают время и могут пропустить ошибки.
- При сопровождении нескольких версий стратегию может потребоваться пересмотреть.

### Риски и митигация

Вероятность и влияние — качественные оценки для предлагаемого процесса.

| Риск | Вероятность | Влияние | Митигация |
| --- | --- | --- | --- |
| Конфликты в крупных ветках | Средняя | Среднее | Делить задачи на небольшие PR, получать изменения `main` перед слиянием, согласовывать правки общих файлов. |
| Неработоспособный код в `main` | Средняя | Высокое | Проверять запуск и `/health`, фиксировать результат в PR, получать approval; после внедрения CI добавить обязательные проверки. |
| Задержка ревью | Средняя | Среднее | Предлагаемый срок первого ответа — 24 часа. При занятости ревьюера согласовать срок и продолжить независимую задачу; собственное approval не заменяет ревью. |
| Правила защиты существуют только в документации | Средняя | Высокое | Владельцу проверить настройки `main`, включить перечисленные ограничения и зафиксировать результат до принятия ADR. |
| Преждевременное слияние ADR | Низкая | Среднее | На этом этапе выполнить только push ветки; PR и межкомандное ревью провести на практике №2. |
